# Ninja (ZX): главный цикл и отрисовка

Разбор по трассировке 14.11.2026. Снимок после загрузки ленты, 6000 кадров (2 минуты)
со сценарием клавиш: меню → «1 Keyboard» → «0 Start», ходьба, удары, прыжки, переходы
по комнатам (Torii in the Sea → Walkway → Torii). Скриншоты: `docs/trace/play_montage*.png`.

Сводки прогона: `docs/trace/report.txt` (порты, вызовы ПЗУ), `timing.txt` (такты),
`calls.txt` (кто кого вызывает и сколько раз), `ranges.txt` (выполненный код).
Первый прогон: 2814 адресов, 75 участков. Остальные ветки — раздел «Покрытие веток».

## Как повторить

```sh
tools/.venv/bin/tap2sna.py orig/spectrumcomputing/Ninja.tzx/Ninja.tzx build/snap/ninja.z80
K="50-54:1,80-84:0,200-700:P,700-760:P+ENTER,760-900:O,900-960:O+ENTER,960-1000:Q,1000-1300:P,1300-1340:Q+P,1340-1400:A,1400-1450:A+ENTER,1450-2000:P,2000-2040:ENTER,2040-2500:O,2500-2600:Q,2600-3500:P,3500-3600:Q,3600-4500:O,4500-6000:P"
tools/.venv/bin/python tools/run_trace.py build/snap/ninja.z80 build/trace/hist --frames 6000 --keys "$K" --hist
tools/.venv/bin/python tools/analyze_trace.py build/trace/hist build/snap/ninja.z80
tools/coverage.sh                                     # все сценарии → build/trace/all
tools/.venv/bin/python tools/analyze_trace.py build/trace/all build/snap/ninja.z80
tools/.venv/bin/python tools/gen_ctl.py build/trace/all/ranges.txt > src/ninja.ctl
tools/.venv/bin/python tools/build_skool.py          # проверка 49 024 байт + asm/html
tools/.venv/bin/python tools/dis_hist.py build/snap/ninja.z80 build/trace/hist/hist.txt ED23-EDC1
```

`run_trace.py` — без окна и звука; `--keys "кадры:КЛАВИША[+КЛАВИША]"`, `--shots` пишет SCR,
`tools/montage.py` склеивает PNG. Kempston читается как 0 (иначе «все кнопки нажаты»).

## Старт

```
5CEF  64×NOP          RET загрузчика попадает сюда (SP=0)
5D2F  JP $D714 → JP $EBE9
EBE9  GAME_START: LD SP,0 / DI / LD A,R → RNG_SEED / CLEAR_SCREEN / рамка / меню
EC0E  MENU_CHOICE (0–5) → CONTROL_TYPE $E1EC
EC2D  новая игра: IDOL_ROOMS (6 случайных комнат 1..20, кроме 11), обнуление таблиц,
      счёт "00000", ROOM=6, ENTER_ROOM, CLEAR_HUD_ATTRS
ED23  MAIN_LOOP
```

Прерывания: IM 1, обработчик ПЗУ `$0038` (поэтому багфикс восстанавливает `IY=$5C3A`).
**HALT нигде нет** — главный цикл не синхронизирован с кадром и идёт сколько успевает.

## Главный цикл `$ED23`

```
ED23  RANDOM                     перемешать ГСЧ
ED26  CHECK_HITS                 столкновения бойцов → $E8A9/$E8AA
ED2D  HIT_HANDLER   если $E8A9
ED34  HIT_HANDLER2  если $EE8C
ED3B  HERO_DEATH    если $EE8E
ED3E  MOVE_ENEMIES               бойцы 5..1
ED41  HERO_ACTION
ED44  ENEMY_STATE
ED47  ANIMATE_ACTORS
ED4A  ANIMATE_ALL
ED4D  DRAW_ACTORS                ← вся отрисовка, см. ниже
ED50  ENEMY_AI                   пишет «нажатия» врагов в HERO_INPUT+n
ED5D  IDOLS_HELD=7 и ROOM=4 → WINNER ($F091)
ED70  ROOM=10 → IDOL_IN_ROOM, иначе IDOL_ROOM_CHECK → IDOL_IN_ROOM при C
ED83  SCORE_TICK (+UPDATE_HUD, если были очки)
ED89  READ_CONTROLS, если герой «свободен» ($E1ED=0)
ED9D  клавиша G — пауза, F — рестарт (JP GAME_START)
EDBF  JP $ED23
```

Управление единообразно: у каждого бойца есть байт «нажатий» `HERO_INPUT+n` (`$E1ED`
герой, дальше 5 врагов). Герою его заполняет `READ_CONTROLS`, врагам — `ENEMY_AI`.
Дальше движение и анимация общие. Для порта это удобно: ввод меняется в одном месте.

## Отрисовка (≈ 75 % процессора)

Двойной буфер: **`BACK_BUFFER` = адрес экрана + `$1B00`** (`$5B00–$72FF`, та же
раскладка, что у экрана ZX). За проход цикла:

1. `DRAW_FIELD` — карта тайлов `TILE_MAP` (`$8BF7`, байт на знакоместо, 0 = пусто)
   → в буфер, тайл 8 байт из `TILE_GFX $D00C`. Обычно 320 клеток (строки 10–19,
   игровое поле); при флаге `$E2D4` — все 672 (21 строка).
2. `ACTOR_FRAMES` — для 6 бойцов кадр из `FRAME_TABLE $DA0C`, адреса через
   `ROW_TABLE $D717`.
3. `BLIT_ACTORS` — спрайт с маской (`AND маска / OR спрайт`) в буфер.
4. Метательное оружие (`PROJECTILES_*`, 3 штуки в `$E866`).
5. `COPY_ACTORS_TO_SCREEN` — прямоугольник 7 байт × 60 (66) строк на бойца из буфера
   на экран через `LDI`.
6. `CLEAR_ACTOR_RECTS` — эти же прямоугольники в буфере обнуляются; фон в них
   восстановит `DRAW_FIELD` в следующем проходе.

Атрибуты в игре почти не меняются: спрайты одноцветные поверх цветного фона
(цвет — от знакоместа).

## Время

Проход главного цикла (p50) **256 700 тактов = 3,67 кадра** → игра ≈ 13,6 «тиков» в
секунду; p90 — 5,9 кадра (смена комнаты, звук).

| подпрограмма | доля |
|---|---|
| DRAW_FIELD | 40,4 % |
| BLIT_ACTORS | 9,6 % |
| ПЗУ (прерывание IM 1, KEY-SCAN, BEEPER) | 9,1 % |
| COPY_ACTORS_TO_SCREEN | 7,8 % |
| ROOM_TRANSITION | 6,6 % |
| NEXT_ROW_SHADOW + NEXT_ROW | 10,1 % |
| CLEAR_ACTOR_RECTS | 5,1 % |
| вся логика игры вместе | < 10 % |

## Выводы для порта на Вектор

- Логики мало и она дешёвая; почти всё время — перерисовка поля. `DRAW_FIELD` каждый
  проход заново кладёт все непустые тайлы 10 строк поля — это главный кандидат на
  замену: на Векторе восстанавливать фон только под прямоугольниками бойцов
  (или держать чистый фон в другой плоскости/странице).
- Раскладка экрана ZX (`NEXT_ROW` с прыжками через трети) на Векторе не нужна:
  столбцы по 256 байт, следующая строка — `DEC L`/`INC L`.
- Синхронизации с кадром нет — на Векторе можно сразу делать фиксированный темп
  (например, тик каждые 3–4 кадра) и не зависеть от числа бойцов.
- Звук: только BEEPER (`CLICK`, `ROOM_SOUND` через ПЗУ, `SOUND_HIT` через `OUT ($FE)`).
  Багфикс 1 (EI из ПЗУ BEEPER) на Векторе снимается сам: своих вызовов ПЗУ нет.
- Багфикс 2: `ROOM` (`$E4BA`) — 14-й байт записи бойца 5; при переносе выделить
  отдельную ячейку.

## Таблица бойца (15 байт, `ACTORS $E461`, 6 записей)

Предварительно, по `ACTOR_FRAMES`/`BLIT_ACTORS`:
`+0` X (знакоместо), `+1` Y/кадр по строкам, `+2/+3` высота/ширина спрайта,
`+4/+5` адрес в буфере, `+6/+7` указатель данных кадра, `+8` состояние (0 = активен,
`$FF` = …), `+9` номер кадра, `+A/+B` адрес на экране, `+E` у записи 5 — это `ROOM`.

`--at КАДР@PC:АДРЕС=ЗНАЧ` — разовая запись в память, когда PC дошёл до адреса
(нужна, потому что `CHECK_HITS` сбрасывает флаги в начале каждого прохода).
s9 честно прошёл много комнат (пагода, Shijo Entrance, Hallway…) и подобрал 2 идола:
`docs/trace/random_walk.png`.

Итог: **3563 адреса в ОЗУ, 52 участка, 7 КБ кода** (первый прогон: 2814 / 75 / 5,5 КБ).

Что выяснилось:
- **Жизнь одна.** Нокаут героя → `HERO_KO` → 5 проходов `HERO_DEATH` → ждёт, пока
  `PENDING_POINTS` ($E4C2) не перетекут в счёт → GAME OVER → любая клавиша → `GAME_START`.
- Удар: `HIT_HANDLER` вычитает из энергии (`+$0C`) случайные 3..10; при 0 — нокаут.
- `$EA76` — это не выход из комнаты, а **`SCORE_TICK`**: по 2 очка за проход из
  `PENDING_POINTS` в цифры счёта (поэтому счёт «набегает»).
- WINNER: `IDOLS_HELD=7` в комнате 4.

**Не пройдено** (стоит `b`): мелкие куски `$EF02–$EF1B`, `$F185–$F1B3`, `$F610–$F62E`,
`$FB06–$FB29` и т.п.; дыры в `$E021–$E0E4`, `$E37E–$E4DE`, `$E828–$E8AA`, `$F0A6–$F0F1`,
`$FECA–$FF47` — таблицы клавиш, переменные, тексты, таблицы ударов.

## Комнаты и дыры

- `ENTER_ROOM(A)` ($F699) переходит к **соседней** комнате в направлении A:
  0 — влево (X<2), 1 — вправо (X≥$19), 2 — вверх, 3 — вниз (`ROOM_EXITS`, `HOLE_EXITS`).
- Новая игра: `ROOM=6`, `ENTER_ROOM(1)` → **старт в комнате 4** (Torii in the Sea). Туда же
  надо вернуться с 7 идолами (WINNER).
- `HOLES` ($DBB5): на комнату 2 байта — X дыры в потолке и X дыры в полу (0 — нет).
  Дыры в полу: комнаты 7, 10, 12, 14, 15, 17, 20; в потолке: 8, 9, 12, 14, 15, 20.
  Подъём — «вверх» под дырой (X..X+2), спуск — «вниз» над дырой в фазе приседа 2
  (`$E4CD`). Снимки: `docs/trace/floor_hole.png`, `ceiling_hole.png`.
- «Особый боец» `$FE56` оказался **`DRAW_HOLES`**: каждый проход рисует дыры в задний
  буфер (3 байта × 16 строк `$FF` + края из `$DBDF`/`$DBFF`). Флаги `$E4D9/$E4DA` —
  это X дыр текущей комнаты, их пишет `SETUP_HOLES` одним словом.
- Таблица подстановки для запуска с нужной комнаты (`--at 0@ED1D:E4BA=N` → комната):
  0→16, 1→15, 2→6, 3→8, 4→5, 5→3, 6→4, 7→17, 8→2, 9→9, 10→10, 11→12, 12→18, 13→14,
  14→14, 15→0, 16→16, 17→17, 18→9, 19→1, 20→20.

## Ошибки оригинала

1. **Враги не попадают по герою в ближнем бою.** В `CHECK_HITS` цикл «враги → герой»
   (`ENEMY_HITS_LOOP`, $EF4E) открывается условием `поле +7 = 0` (`LD HL,$E4B3` —
   запись 5, +7). Но +6/+7 — указатель кадра, его каждый проход пишет `ACTOR_FRAMES`
   (`$91xx`/`$92xx`), он никогда не 0. Симметричный цикл «герой → враги»
   (`HERO_HITS_LOOP`) смотрит +8 (состояние). Проверено: с `$EF4F: $B3→$B4` враг,
   стоящий вплотную, снимает энергию `0F→0C→05→00` и через ~4 с — GAME OVER (s12).
   Без правки за 30 000 кадров случайной игры (s13) энергия героя не убыла ни разу;
   попаданий метательным оружием (`$F30C`, `$F36C`) тоже не было.
   В багфиксе Bandit/Einar Saukas этого нет.

   **Сверка с CPC (14.11): это ошибка ZX-переноса, а не замысел.** CPC-версия
   (`NINJA3.BIN`, грузится с `$0040`, старт `$5672`; одинаков на дисках MT0015, 1987 и
   1990 [f1]) содержит тот же `CHECK_HITS` почти команда в команду (`$6FD0` ↔ `$EF3F`,
   `tools/cmp_zx_cpc.py EF3F 6FD0 40`). Но у CPC данные бойцов — **массивы по полям**
   с шагом 1, а не записи по 15 байт:

   | | CPC | ZX |
   |---|---|---|
   | герой X | `$7442` | `$E461` (+0 записи 0) |
   | враги → герой, старт B=5 | `LD HL,$7459` = `$7454+5`, `DEC HL` | `LD HL,$E4B3` = запись 5 **+7**, `-15` |
   | герой → враги, старт B=1 | `LD HL,$7455` = `$7454+1`, `INC HL` | `LD HL,$E478` = запись 1 **+8**, `+15` |

   У CPC оба цикла проверяют один массив `$7454` (состояние бойца; им же пользуются
   и другие циклы по врагам, `LD HL,$7459` в 8 местах). При переводе в записи ZX
   адрес второго цикла пересчитан верно (+8), первого — на 1 меньше (+7). Правильно —
   `$E4B4` (`$EF4F: $B3→$B4`). На CPC враги бьют героя; в ZX-издании не бьют.
   **Проверено и в работе (MAME cpc6128, `tools/cpc/run.sh`):** герой стоит вплотную к
   каратисту без ударов — каратист снимает энергию, на ~кадре 4000 герой лежит, затем
   GAME OVER (около 6 с от первого контакта): `docs/trace/cpc_enemy_kills_hero.png`.
   Массивы CPC по памяти: `$7442` — X (по 2 байта), `$7454` — состояние (0 — активен),
   `$745A` — тип/энергия (`$F0+тип`, у героя `$F4`). Издание 1990 `NINJA.BIN` не смотрел.

2. **Падение при включённых прерываниях** — следствие ошибки 1 багфикса (`EI` в конце
   ПЗУ `BEEPER`, после щелчка меню прерывания включены всю игру). `CLEAR_SCREEN`
   ($DFE3) заливает `$4000–$57FF` через `PUSH` с `SP` от `$5800` вниз. Если прерывание
   IM 1 придёт, когда `SP` ≈ `$4008`, обработчик ПЗУ кладёт слова ниже `$4000` — в ПЗУ,
   они теряются, `RET` уходит на `$A199` → `$0000`, Спектрум перезагружается.
   Воспроизведение (s13 без правки, кадр 3531), след — `docs/trace/crash_ring.txt`:
   ```sh
   tools/.venv/bin/python tools/run_trace.py build/snap/ninja.z80 build/trace/crash --hist \
     --frames 3540 --keys "50-54:1,80-84:0,$(tools/.venv/bin/python tools/randkeys.py 150 30000 2)" --ring A199
   ```
   С правкой из `Ninja(BUGFIX).tzx` (`CALL $03F7`) прерывания не включаются, падения нет.
   Игре прерывания не нужны вовсе (клавиатура опрашивается напрямую).
3. **Номер комнаты в таблице бойцов** (`ROOM` = байт 14 записи 5) — из багфикса.

Для порта: прерывания на Векторе свои, ошибка 2 исчезает сама; ошибку 1 исправлять —
так задумано авторами (CPC), игра станет труднее: рядом с врагом стоять нельзя.
